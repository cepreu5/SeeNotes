# SeeNotes — API за търсене в бележките (Google Apps Script)

Самостоятелен **read-only** HTTP endpoint за търсене в бележките на SeeNotes.
Приложението (`uni/`) е чисто статичен PWA без сървър, затова търсенето е
отделен Apps Script проект, който работи от името на собственика на папката и
чете директно от Google Drive.

Скриптът **никога** не създава, променя, трие или мести файлове. Манифестът
иска само `drive.readonly` (Google сам не позволява запис в Drive) и
`script.external_request` (нужен на `UrlFetchApp` за пакетното четене — виж
по-долу). Външните извиквания са само GET към Drive API v3: изтегляне на
съдържанието на файл (`files/<id>?alt=media`), пълнотекстово търсене в списъка
с файлове (`files?q=...`) и акаунтът на Drive (`about?fields=user`).

## Файлове

| Файл | Какво е |
| --- | --- |
| `notes-api.gs` | Кодът: `doGet(e)` |
| `appsscript.json` | Манифест: Web App, изпълнява се от собственика, достъп „Anyone“, часова зона Europe/Sofia |
| `test/local-test.js` | Локален тест (чист Node, без `npm install`) |
| `test/fixtures/` | Примерни `note.txt` / `board.txt` файлове, вкл. един повреден |

## Инсталиране

1. Отвори <https://script.google.com> → **Нов проект** (със същия Google акаунт,
   в чийто Drive е папката `CX-Notes`).
2. **Project Settings** → отметни *Show "appsscript.json" manifest file in editor*.
3. Замени съдържанието на `appsscript.json` с файла от тук.
4. Замени `Code.gs` със съдържанието на `notes-api.gs` (името на файла в
   проекта няма значение).
5. **Project Settings → Script Properties → Add script property**:
   - `API_TOKEN` = дълъг случаен ключ, например от
     `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
     Без `API_TOKEN` всяка заявка връща `unauthorized`.
   - (по избор) `FOLDER_ID` = ID на конкретната папка, ако имаш няколко папки
     с име `CX-Notes`. Без него се търси `CX-Notes`, а ако не съществува —
     старата `multinotes_data` (както прави и приложението).
6. **Deploy → New deployment → Web app**. Execute as: *Me*, Who has access:
   *Anyone*. При първото пускане Google ще поиска разрешение за четене на Drive.
7. Копирай URL-а на Web App-а (`https://script.google.com/macros/s/.../exec`).

### Обновяване на СЪЩЕСТВУВАЩ deployment (URL-ът остава същият)

1. Отвори проекта в редактора на Apps Script.
2. Замени кода със съдържанието на `notes-api.gs` (и `appsscript.json` с файла
   от тук, ако е променен) → **Save**.
3. Избери функцията `doGet` → **Run** веднъж и приеми новото разрешение.
   (След добавянето на `script.external_request` Google еднократно ще поиска
   разрешение „Connect to an external service“. Грешката от самото пускане
   без параметри е без значение — важното е разрешението да е прието.)
4. **Deploy → Manage deployments** → молива (Edit) при съществуващия deployment
   → **Version: New version** → **Deploy**.

URL-ът `/exec` не се променя. **Не ползвай „New deployment“** — той създава
друг deployment с различен URL, а клиентите (и проксито) продължават да сочат
към стария, който сервира старата версия на кода.

## Използване

```
GET https://script.google.com/macros/s/<ID>/exec?key=<API_TOKEN>&q=договор
```

`curl` трябва да следва пренасочването: `curl -L "<URL>?key=...&q=..."`.

| Параметър | Описание |
| --- | --- |
| `key` | Ключът от `API_TOKEN` (задължителен) |
| `q` | Текст за търсене. Няколко думи, разделени с интервал = **всички** трябва да се срещат. Без значение от главни/малки букви (и за кирилица). Без `q` — само метаданни (health check) |
| `board` | Заглавие на борд (напр. `Работа`) или неговото id / gdid |
| `from`, `to` | `YYYY-MM-DD`, филтър по датата на бележката (`date`, в часова зона Europe/Sofia) |
| `limit` | Брой резултати, по подразбиране 20, максимум 100 |
| `mode` | `auto` (по подразбиране), `index` или `scan` — виж „Бърз път през индекса на Drive“. Непозната стойност = `auto` |
| `budget` | Бюджет по време в ms за четенето, по подразбиране 18000, ограничен до 3000–25000 |
| `batch` | Файлове в един `UrlFetchApp.fetchAll`, по подразбиране 40, ограничен до 5–100 |
| `debug` | `debug=1` добавя обект `timing` в отговора (виж по-долу). Без него нищо допълнително не се връща |

Невалидна стойност на `budget` / `batch` (не е число) = стойността по
подразбиране; число извън границите се приближава до най-близката граница.

### Отговор при търсене

```json
{
  "ok": true,
  "folder": "CX-Notes",
  "query": "договор",
  "count": 1,
  "truncated": false,
  "scanned": { "noteFiles": 812, "notes": 812, "boards": 7, "corrupt": 0, "capped": false },
  "totalFiles": 812,
  "partial": false,
  "mode": "scan",
  "account": "owner@gmail.com",
  "driveAccount": "owner@gmail.com",
  "results": [
    {
      "id": 102,
      "gdid": "1AbC...",
      "title": "Договор за наем",
      "board": "Лични",
      "boardId": "1XyZ...",
      "date": "2026-01-05",
      "modified": "2026-01-05T12:00:00+02:00",
      "matchIn": "title",
      "snippet": "…около 200 знака около първото съвпадение…",
      "text": "пълният текст на бележката",
      "driveUrl": "https://drive.google.com/file/d/1AbC.../view"
    }
  ]
}
```

- `gdid` е Drive ID на самия `note.txt` файл на бележката, `id` — вътрешното id.
- `title` се извежда от текста, както в приложението: частта преди `|`, иначе
  първият непразен ред (бележките нямат отделно поле за заглавие).
- `board` е заглавието на борда от `board.txt`, `boardId` — суровата стойност `boardid`.
- `matchIn`: `title`, `text` или `both`.
- Сортиране: първо съвпаденията в заглавието, после по `datemod` (най-новите отгоре).
- `truncated: true` — има още резултати над `limit` или сканирането е спряло на
  тавана (`scanned.capped: true`, 2000 файла / `budget`).
- `scanned.corrupt` — брой непарсваеми `note.txt` файлове (прескачат се).
- `totalFiles` — колко `note.txt` файла е трябвало да се прочетат (при
  `mode: "index"` — броят кандидати от индекса); `scanned.noteFiles` — колко
  реално са прочетени преди бюджетът да свърши.
- `partial: true` — четенето не е стигнало до края (бюджет по време, таван
  от 2000 файла или повече от 1000 кандидата от индекса). Тогава и
  `truncated: true`.
- `mode` — кой път е използван реално: `index` или `scan`.
- `account` / `driveAccount` — акаунтът, от чието име работи скриптът:
  `Session.getEffectiveUser().getEmail()` и `user.emailAddress` от Drive
  `about`; `null` при грешка или празна стойност (никога не чупят заявката).
  Бележка: без scope `userinfo.email` Apps Script обикновено връща празен
  `account` (→ `null`), а `driveAccount` работи само с `drive.readonly`.

Без `q` отговорът е `{"ok":true,"folder":"...","scanned":{...},"count":0,"truncated":false,"totalFiles":...,"partial":false,"mode":"scan","account":...,"driveAccount":...,"results":[]}`.

### `debug=1`

Добавя обект `timing` (всички времена са в ms):

| Поле | Какво е |
| --- | --- |
| `folderMs` | Намиране на папката |
| `filesListMs` | Списъкът с `note.txt` (DriveApp) и/или търсенето в индекса на Drive |
| `filesTotal` | Брой намерени `note.txt` записи (= `totalFiles`) |
| `batches` | Време на всяка партида при четенето на бележките |
| `bytesRead` | Прочетени байтове от `note.txt` файловете |
| `boardsMs` | Зареждане на бордовете |
| `totalMs` | Общо време на заявката в скрипта |

### Бърз път през индекса на Drive

При `mode=auto` (по подразбиране) скриптът първо пита Drive API v3
(`files.list`) кои `note.txt` в папката съдържат всички думи:

```
'<folderId>' in parents and name = 'note.txt' and trashed = false
  and fullText contains '<дума1>' and fullText contains '<дума2>' ...
```

и чете само тези файлове. Съвпадението, snippet-ът и филтрите пак се
проверяват от скрипта точно както при пълното сканиране — индексът само
стеснява кои файлове се четат, затова резултатите са в същия формат (и
скритата част на скритите бележки пак не се търси). Ако индексът върне
грешка, отговор ≠ 200 или нула кандидати, `auto` пада на пълно сканиране.

- `mode=scan` — винаги пълно сканиране (старото поведение).
- `mode=index` — само индексът; нула кандидати = нула резултати, а
  недостъпен индекс = `{"ok":false,"error":"index_unavailable"}`.
- Индексът на Drive търси по думи, не по поднизове: `догово` може да не
  намери `договора`, а току-що променен файл може да се появи в индекса с
  малко закъснение. Ако индексът върне поне един кандидат, `auto` не
  сканира останалите файлове — при нужда от пълно покритие ползвай
  `mode=scan`.
- Без заявка (`q` липсва — health check) винаги се прави пълно сканиране.

### Какво НЕ се връща

- Бележки в Кошчето (`status: 1`).
- Скритата част на скрити бележки (`pass: true`): търси се и се връща само
  видимото превю преди `|`.
- Никакви други полета от обекта на бележката (`pass`, `uiState`, …) и никога ключът.

### Грешки

| Ситуация | Тяло |
| --- | --- |
| Липсващ или грешен ключ | `{"ok":false,"error":"unauthorized"}` |
| Невалидна дата във `from`/`to` | `{"ok":false,"error":"bad_date"}` |
| Папката не е намерена | `{"ok":false,"error":"folder_not_found"}` |
| `mode=index`, а индексът на Drive е недостъпен | `{"ok":false,"error":"index_unavailable"}` |
| Неочаквана грешка | `{"ok":false,"error":"internal_error"}` |

## Важни ограничения на Apps Script

- **HTTP статусът винаги е 200.** Web App не може да връща 401/500 — логиката
  избира статус (401, 400, 404, 500), но навън той е само в тялото. Проверявай
  полето `ok`.
- **Хедърът `X-API-Key` на практика не стига до скрипта** — Apps Script не
  подава хедърите на заявката в `doGet(e)`. Кодът го проверява, ако някога
  бъде подаден, но в реална употреба ползвай параметъра `key`.
- Ключът в URL може да остане в история/логове на клиента — пази URL-а като
  парола и сменяй `API_TOKEN` при съмнение (промяната важи веднага, без нов deploy).
- Всяка заявка чете всички `note.txt` файлове наново (търсенето е пълно, без
  кеш). Съдържанието се чете **пакетно**: `UrlFetchApp.fetchAll` изтегля до 40
  файла паралелно през Drive API (`alt=media`) с OAuth токена на скрипта
  (`ScriptApp.getOAuthToken()`). Преди това всеки файл беше отделна HTTPS
  заявка през DriveApp — при ~93 файла това бяха 30–45 s; сега са 3 партиди
  за бележките + 1 за бордовете, т.е. няколко секунди.
- Резервни пътища, със същия резултат: отговор ≠ 200 или грешка за даден файл
  → този файл се чете през DriveApp; ако няма OAuth токен → всички файлове се
  четат последователно през DriveApp (бавно, както преди). Файл, който не може
  да се прочете и по двата начина, се брои в `scanned.corrupt`.
- **Таван от 30 s пред Web App-а.** Проксито пред Web App-а чака отговор
  най-много 30 s и това не може да се промени — след това връща
  `502 upstream_error`. Към времето на скрипта се добавят и няколко секунди
  на самия Apps Script (стартиране, пренасочване), затова `doGet` трябва да
  приключи под ~25 s. Измерено на 25.09.2026 с бюджет 22 s: 23–32 s, т.е.
  около половината заявки падаха.
- **Бюджет по време (`budget`, по подразбиране 18 s, най-много 25 s).**
  Броенето започва веднага след проверката на ключа и включва папката,
  бордовете, индекса и бележките. Преди всяка партида скриптът спира, ако
  бюджетът е изчерпан **или** ако средното време на досегашните партиди
  показва, че следващата би го надхвърлила — така една партида не може да
  прескочи бюджета (първата партида няма мярка и се пуска, ако има време).
  При спиране връща частичен резултат с `partial: true` /
  `scanned.capped: true` / `truncated: true` — по-добре непълен отговор,
  отколкото `502` от проксито. С `debug=1` се вижда къде отива времето.

## Локален тест

```
node apps-script/test/local-test.js
```

Тестът подменя `DriveApp`, `PropertiesService`, `ContentService`, `Utilities`,
`ScriptApp` и `UrlFetchApp` с фалшиви обекти, които четат от `test/fixtures/`,
и извиква `doGet`. Фалшивият Drive хвърля грешка при всеки метод за запис, а
фалшивият `UrlFetchApp.fetchAll` отговаря само на GET media изтегляния и хвърля
при всеки друг URL или метод. Проверява се и че пакетният път дава идентичен
отговор с последователния, резервните пътища, бюджетът по време (с фалшив
часовник), `budget`/`batch`, `debug`, заявката към индекса на Drive (вкл.
екраниране и AND на думите), fallback-ът на `auto` при нула кандидати и
`account`/`driveAccount`. Печата PASS/FAIL за
всеки тест и излиза с код ≠ 0 при провал.
